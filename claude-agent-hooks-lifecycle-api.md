Two distinct hook systems exist. Do not mix them.

1. **Classic hooks** ("settings hooks"): external handlers (`command`, `http`, `prompt`, `agent`, `mcp_tool`) configured in settings, plugin `hooks/hooks.json`, or agent/skill frontmatter. JSON in, JSON/exit code out.
2. **Function hooks / "mods"** (early access, introduced 2.1.287): in-process TypeScript hooks `($, e, next)` registered through `register(on, options)`. Classic events are also exposed to mods as `classic.<Event>`.

## Executive summary

- Classic hooks: about 33 named events (the d.ts `HookInput` union lists 33). Transport is stdin JSON plus exit code plus stdout JSON for `command`; HTTP POST for `http`. Documented in CHANGELOG and typed in the d.ts; the prose docs shipped in `plugins/plugin-dev` are stale.
- Mod hooks: three event families (engine call-site events, `classic.*`, and "op" events where every `$` call is itself hookable) with a typed, chain-of-responsibility model, a 10 s per-hook budget, and fail-skip isolation.
- Subagent detection on classic hooks: `agent_id` present means subagent (`documented`, d.ts `BaseHookInput`). Parent identity is **not** in classic hook stdin (`unknown`, absent from all evidence). Parent link exists for mods (`parentAgentId` on `agent.spawn`, `AgentInfo.parentId`) and in OTel/HTTP headers.
- Largest risks for consumers: stale plugin-dev docs, no documented hook ordering or precedence, several per-event stdin schemas that are only partly typed (see Unknowns), and mods being explicitly "early access, may change".

## Evidence and confidence model

Labels: `documented` (public contract: d.ts JSDoc, CHANGELOG statement, repo prose), `tested` (asserted by a repo test), `observed` (seen in shipped example or plugin code, or implementation detail), `inferred`, `unknown`.

Notes on how labels were applied here:

- The public d.ts (`mods/types/claude-code.d.ts`) is generated by the product (`/plugin-types`) and is treated as `documented`, but it carries an "early access, may change without notice" banner.
- CHANGELOG lines are `documented` for *that* behavior at *that* version only. A CHANGELOG line usually describes a delta, not a full schema.
- Very little is `tested`: only `mods/*/tests` (mod behavior, not harness delivery) and small plugin-dev shell scripts.
- Public-contract vs implementation: d.ts, CHANGELOG, README = public-contract material. Shipped plugin code (hookify, security-guidance, ralph-wiggum) = implementation of consumers, i.e. `observed` behavior of the harness as seen by them.

### Mod events

Mod events have no shared JSON envelope; each handler receives `e` (frozen typed object), `$` (capability object), and `next`. Commonly pinned fields: `agentId?` (loop identity, absent on main loop), `turnId`, `tool_use_id`, `provider`/`origin`. See schemas below.

## Subagent identity and parent correlation

### How a subagent starts and stops

- Started by the Agent tool (also forks, teammates, plugin `$.agent.spawn` since mods; teammate spawn added 2.1.289). Evidence: d.ts `AgentSpawnInput`, CHANGELOG. `documented`.
- Boundary events: classic `SubagentStart` and `SubagentStop`; mod `agent.spawn` (before start) and the subagent's own `turn.complete` carrying the same `agentId` (after). `documented`.
- Nesting: nested subagents are keyed by the spawning Agent `tool_use_id` in stream-json (2.1.219); `parentAgentId` on `agent.spawn` points to the immediate spawner. Whether classic hooks carry depth: `unknown`. No depth field exists in `AgentInfo` (`documented` absence in typing). Maximum depth/concurrency: `unknown`.

### Decision procedure for one raw payload

Classic (JSON on stdin):

1. If key `agent_id` exists and is a non-empty string: **subagent**.
2. Else if `hook_event_name` is `SubagentStart` or `SubagentStop`: still read `agent_id` (required by the typing); if missing, treat as malformed.
3. Else: **root**. A present `agent_type` without `agent_id` means the main thread of a `--agent` session, which is still root (`documented`, d.ts JSDoc).
4. Parent identity: **not available** in the classic payload. Closest substitute: `session_id` (shared root session, `inferred`) plus, when you saw the earlier root-side `PreToolUse` for the Agent tool, its `tool_use_id`. The classic `SubagentStart` does not carry the spawning `tool_use_id` (`documented` by the typing, which lists only `agent_id` and `agent_type`). Linking by timing is `inferred` and fragile. OTel/HTTP: `parent_agent_id` span attribute and `x-claude-code-parent-agent-id` header exist (`documented`, CHANGELOG 2.1.139, 2.1.145) but are not hook payload fields.

Mods:

1. `e.agentId === undefined` on `tool.call`, `turn.step`, `turn.complete`, `session.compact`: **root** (`tested`: `mods/diff/tests/register.test.ts` "only the main loop's edit opens the pane").
2. Otherwise **subagent**; the id matches `AgentInfo.id`.
3. Parent: on `agent.spawn`, `parentAgentId` (absent = main loop; `observed` in `mods/agents-md/hooks/register.ts`, `documented` in d.ts). Later, `$.agent.list()` gives `AgentInfo.parentId` (immediate parent; absent if main) and `spawnedBy` (plugin name) (`documented`). Parent link points to the **immediate** parent, not the root.

## Security and privacy notes

- Classic stdin carries `tool_input`, `tool_response`, `transcript_path`, `cwd`, prompts (`prompt`), `last_assistant_message`, and `session_crons[].prompt`. A hook that reads `transcript_path` can read the whole conversation (`observed`: ralph-wiggum, hookify).
- Hook output is injected into model context (`additionalContext`, exit-2 stderr). `plugins/security-guidance` prefixes hook-originated text with a provenance banner to reduce prompt-injection confusion (`observed`). Background-task notifications state that no human input occurred (2.1.205).
- Secrets: `http` hooks restrict URLs and env interpolation through managed `allowedHttpHookUrls`, `httpHookAllowedEnvVars`; `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB` strips credentials.
- Mods: `$.settings.read()` returns every key unfiltered, including `env` and helper commands; `$.session.authorize()` returns an opaque credential handle, never the secret; `$.tool.call` `consent` text is treated as the person's words (privilege-relevant); `prompt.context` carries `userEmail` and CLAUDE.md; `session.receive` `untrustedKeys` marks third-party text; MCP server names are untrusted. `mods/sec-default` is designed to keep managed hooks, prompt content and deny rules out of reach of user plugins (`documented`, README).
- Telemetry mod: rows validated against free text; off switches include `DISABLE_TELEMETRY`, `DO_NOT_TRACK`, third-party providers (`tested`).
- Plugin-dev advanced examples (Slack curl, SQL insert of raw input, audit log) show patterns that exfiltrate or log tool data and are SQL-injection prone (`observed`). Do not copy them.
- Payload size limits: stdout over 10,000 chars spilled to disk; `prompt.submit` `context` blocks truncated above 100k each / 200k total; Svg source limit 131072; `OTEL` content max 60 KB default (2.1.214). No stdin size limit documented (`unknown`).

## Consumer implementation checklist

Safe to rely on (`documented`):

- Parse envelope: `session_id`, `transcript_path`, `cwd`, `hook_event_name` always present.
- Subagent detection: `agent_id` key present and non-empty means subagent. Use `agent_id`, never `agent_type`, for this.
- `SubagentStart` and `SubagentStop` always carry `agent_id` and `agent_type`; `SubagentStop` also carries `agent_transcript_path`.
- Correlate tool pairs by `tool_use_id`; correlate prompt grain by `prompt_id` when present.
- Exit 2 blocks (PreToolUse etc.); JSON decisions go on stdout with exit 0.

Needs feature detection or defensive parsing:

- Every field marked optional: treat missing key, `null`, and empty string alike.
- Unknown event names and unknown extra keys: ignore, do not fail (the harness itself tolerates unknown names).
- `permission_mode` values; `Notification.notification_type`; `SessionStart.source` set.
- `prompt` versus `user_prompt`: read `prompt` first, fall back to `user_prompt` only for old harnesses.
- Parent resolution: classic has no field. Use `session_id` plus your own record of the root `Agent` `PreToolUse` `tool_use_id` and timing, and label the link `inferred`. In mods, use `parentAgentId` on `agent.spawn` and `AgentInfo.parentId`.
- Do not rely on ordering between parallel hooks, or on hot-reload behavior, or on a default timeout. Set `timeout` explicitly.
- Do not rely on mod APIs staying stable (early access banner).
- Do not trust `mcp_server.name`, `untrustedKeys` content, or `tool_input` contents; escape before display.
- Do not follow plugin-dev stale examples.
- Stamp your own receipt time and sequence; the payloads carry none.
